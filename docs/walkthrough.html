1. TL;DR — what this is in one page

enrichment-arbiter is a self-hosted engine that decides which data vendor to ask first when you need to fill in a missing piece of information about a person or a company — for example, a work email address or a company's firmographics — and it does so while spending as little money as possible and trusting the answer as much as possible.

The core idea is a dynamic waterfall. Instead of always calling the same vendor, or calling all of them and paying everyone, the engine:

  1. checks a cache so it never pays twice for the same person;
  2. ranks every vendor for this specific task and customer segment by a score that mixes quality, cost, and speed;
  3. calls vendors one at a time, cheapest-best first, within a dollar budget;
  4. verifies the returned email/phone before accepting it;
  5. stops at the first verified hit, and logs every attempt;
  6. learns from the outcomes — and from downstream bounces — so the ranking improves over time;
  7. occasionally explores a lower-ranked vendor to discover if it has quietly gotten better.

The single number at the center of everything is ECPVH — Effective Cost Per Verified Hit — the expected dollars you must spend to walk away with one verified, working data point. Vendors are ordered by a composite routing score that rewards yield and penalizes both cost and latency.

Proven on real data. A live run asked Hunter for a person at stripe.com and got back an MX-verified address in 2,391 ms for about $0.02. The same lookup run a second time was served from cache at $0.00 with no API call.

It is deliberately not a cloud SaaS. It is a CLI-first engine that lives in this repo, keeps its state in a local SQLite file, reads secrets from the shared .env, and is invoked the same way Hermes invokes every other engine in this workspace.

3. The problem and the purpose

The problem

A revenue team wants to email or call a list of people. The list is missing work emails and phone numbers. Several vendors sell that data: Apollo, Hunter, Prospeo, Findymail, Clearbit, PeopleDataLabs, and many more. They disagree with each other, they cost different amounts, they are better or worse in different countries and company sizes, and their databases change over time.

The naive approaches all waste money or trust:

  • Always use vendor A. Simple, but overpays and gets whatever A's coverage happens to be.
  • Call everyone and merge. Maximum coverage, but you pay every vendor for every record.
  • Static waterfall (A then B then C forever). Better, but the order was decided once and never adapts when B improves, A degrades, or a country's coverage shifts.

The purpose of this engine

Make the "which vendor first" decision data-driven, cost-aware, continuous, and auditable — and do it inside our own infrastructure so spend, data, and logic stay under our control.

$
Minimize cost per working data point, not per call
✓
Trust only verified values, not raw vendor claims
↺
Learn continuously from production outcomes and bounces
⚖
Adapt per task and per segment, not one global order
⏻
Fail safe: never crash the pipeline on a vendor error
🔒
Self-hosted: keys, data, and decisions stay local

What it is not

  • It is not a database of people. It does not own the data; it orchestrates vendors that do.
  • It is not a CRM. It returns enriched records; a pipeline writes them where they belong.
  • It is not (yet) a web service. Today it is a command-line engine; an HTTP layer is a later phase.

4. Architecture and data flow

Two planes, one database

Conceptually there are two planes. In this implementation both run inside one process, but they are cleanly separated in code so they can later be split.

PlaneRuns whenModulesJob
Execution planeOn every lookuprouter.py, verifier.py, providers/*Serve a cached answer or run the waterfall and verify the result.
Control planePeriodically / on demandevaluator.pyRecompute scores from logs, run golden-dataset probes, absorb feedback.

Request path

Request→ Lookup hash→ Cache?├ hit → Return
Miss→ Rank providers→ ε-explore?→ Budget gate→ Call vendor→ Verify→ Log→ Cache + return

Learning path

enrichment_logs→ recalc (every 20 logs / on demand)→ provider_scores→ next ranking
Downstream bounce→ feedback→ mark log + evict cache→ recalc

Because scoring is recomputed from immutable logs, the system can always be rebuilt from history. The scores are a cache of the logs, not a second source of truth.

6. The math, derived from scratch

Read this section top to bottom. Each concept builds on the previous one. All numbers match evaluator.py exactly; the worked examples use the real Hunter run.

6.1 The two rates every vendor has

For a given vendor, task, and segment, over a rolling 30-day window, we count:

  • attempts — how many times we called it;
  • matches — how many calls returned any non-null data;
  • verified hits — how many returned data that passed verification;
  • bounces — how many of those values later hard-bounced in production.

Match rate answers "when I call, how often do I get something?"

Match rate (raw) MatchRate = matchesattempts

Accuracy rate answers "when I get something, how often is it actually usable?"

Accuracy rate (raw) AccuracyRate = verified hitsmatches

6.2 The bounce penalty: a bounce is worse than a miss

A miss costs you a credit and nothing else. A bounce costs you a credit, wastes an email send, and damages your sender reputation, which lowers deliverability for every future email. So each bounce is penalized twice when computing the effective verified count:

Effective verified hits effective_verified = max( 0, verified_hits − 2 × bounced )

The max(0, …) prevents a provider from going negative and keeps the arithmetic well-defined.

6.3 Bayesian smoothing: don't trust tiny samples

If a vendor has been called once and returned one verified email, its raw accuracy is 1.0 — "perfect". That is obviously not trustworthy. Bayesian smoothing injects a small number of imaginary prior observations so a vendor must earn its reputation with real volume.

Our priors are chosen to mean: "assume 4 matches in 10 attempts, and 3 verified among those 4 matches."

Smoothed rates MatchRate = matches + 4attempts + 10     AccuracyRate = effective_verified + 3matches + 4
Why this also happens to simplify beautifully

Multiply the two smoothed rates:

MatchRate × AccuracyRate = matches + 4attempts + 10 × effective_verified + 3matches + 4 = effective_verified + 3attempts + 10

The matches + 4 terms cancel. So the probability that a call yields a verified hit is effectively (verified + 3) / (attempts + 10) after smoothing — a single, stable fraction. This is why the priors also remove the zero-division problem: the denominator is never zero.

Cold-start effect. An untested vendor (attempts = 0) gets the prior score: match 4/10 = 0.40, accuracy 3/4 = 0.75. That is a reasonable "benefit of the doubt", but it means a vendor with one slow success can temporarily rank below completely untested vendors. This is visible in the real scorecard below, and is expected to settle as samples accumulate.

6.4 ECPVH — Effective Cost Per Verified Hit

This is the heart of the economics. We want "dollars per working data point", not "dollars per call".

First, the expected cost of a single call. A call costs cost_per_attempt always, plus cost_per_match only if it matched. So:

Expected cost of one call E[cost per call] = Cattempt + MatchRate × Cmatch

The probability that one call produces a verified hit is MatchRate × AccuracyRate. Cost per successful outcome is expected cost divided by success probability:

Effective Cost Per Verified Hit ECPVH = Cattempt + MatchRate × Cmatch MatchRate × AccuracyRate

Equivalently (and this is the intuition):

ECPVH = CattemptMatchRate × AccuracyRate + CmatchAccuracyRate

Read it as: "you pay the per-match price more often than necessary when accuracy is low, and you pay the attempt price more often when match rate is low."

Worked example — untested Hunter (Cmatch = $0.02, Cattempt = 0):
MatchRate = 4/10 = 0.40  •  AccuracyRate = 3/4 = 0.75  •  product = 0.30
ECPVH = (0 + 0.40 × 0.02) / 0.30 = 0.008 / 0.30 = $0.0267 per verified hit.

6.5 The composite routing score

We want to rank on three things at once: yield (good), cost (bad), latency (bad). Each penalty is normalized by a maximum we are willing to tolerate, so the terms are dimensionless and comparable.

Composite routing score S = w1 × ( MatchRate × AccuracyRate )  −  w2 × ECPVHMaxAllowedCost  −  w3 × p95 latencyMaxAllowedLatency
SymbolValue hereInterpretation
w11.0Reward for yield = the smoothed probability of a verified hit.
w21.0Weight of cost pressure (ECPVH relative to the $0.50 cap).
w30.5Weight of latency pressure (p95 relative to the 5,000 ms cap). Halved because speed matters, but less than money and correctness.
MaxAllowedCost$0.50The cost above which a vendor is considered expensive. Tune to your economics.
MaxAllowedLatency5,000 msThe latency above which a vendor is considered slow.

The score is not a probability. It is a comparable utility: higher is better, and only the order matters for routing. That is why it may be small or negative; it is a ranking device.

6.7 Cold-start floor: never rank a proven failure first

If a vendor has been tried (attempts > 0) but has produced effectively zero verified hits, it gets a hard floor:

Cold-start guard if ( attempts > 0 and effective_verified == 0 ) → S = −999.0

−999 is not "ban". It sorts the vendor last, so it is still reachable at the bottom of the waterfall and by exploration, which is how it can recover. It simply never jumps the queue while it is failing.

6.8 Explore vs exploit: the multi-armed bandit

If we always pick the current best vendor, we never learn that a lower-ranked vendor quietly improved. That is the classic explore/exploit trade-off. We use epsilon-greedy:

Epsilon-greedy selection with probability 1 − ε = 95% → strict descending score (exploit)
with probability ε = 5% → pick a random lower-ranked active vendor and promote it to slot 1 (explore)

Only slot 1 changes, and only among vendors already eligible (active, not cooling). The experiment costs at most one possibly-worse call and buys information that can move the whole ranking. Exploration is logged, so you can tell it apart from normal traffic.

6.9 p95 latency

We care about the tail: a vendor that is usually fast but occasionally hangs for ten seconds is a problem. p95 = the value below which 95% of observations fall. Over the last 100 attempts per scope:

95th percentile (no interpolation) vals = last 100 latency values, sorted ascending
index = int(0.95 × len(vals)) , clamped to the last element
p95 = vals[index]  (default 500 ms if empty)

Example: for latencies 1..100, int(0.95×100) = 95, and the 0-based element is 96. That matches the unit test.

6.10 Circuit breaker

A failing vendor should be given a rest, not hammered. We count consecutive transport failures (HTTP 429, any 5xx, timeouts, exceptions):

  • on each failure: consecutive_failures += 1;
  • at 3 consecutive: set cooldown_until = now + 15 minutes;
  • on any success (2xx): consecutive_failures = 0.

While cooling down, the vendor is filtered out of ranked_providers entirely.

Important distinction. A clean miss (HTTP 200, no data) is not a failure. A missing API key is not a failure either — it is skipped as skipped_unconfigured, with no bill, no breaker increment, and no negative cache. Only real transport problems trip the breaker.

6.11 Caching and TTL

The cache key is:

Cache key lookup_hash = SHA-256( task_type + "|" + normalized_identity )

Normalization lowercases fields, strips https://, paths, and www. from domains, and picks a task-specific identity: email if present, else LinkedIn URL, else name+domain (for people); domain (for companies).

KindTTLWhy
Positive (verified)30 daysVerified emails are stable over a month; job changes are the main churn.
Negative (clean miss)7 daysShorter, so newly-added coverage is discovered soon; long enough to stop re-burning credits.

6.12 Budget gate

Before every vendor call, we check the worst case (assuming it matches):

Pre-attempt budget check spent_so_far + Cattempt + Cmatch ≤ max_budget

If it would exceed, the vendor is skipped with status skipped_budget. Skipping for budget does not create a negative cache entry, because we never actually established that the data is unfindable.

6.13 Feedback: closing the loop with reality

Verification (MX) proves a domain can receive mail. It does not prove the mailbox exists. The only ground truth is what happens after you send. So a downstream bounce event is fed back in:

  1. find the log row(s) whose result_value matches the bounced email (or by request_id);
  2. set feedback = 'bounce' and verified = 0;
  3. delete the matching cache entry so the bad email is never served again;
  4. recompute scores; the bounce penalty reduces that vendor's effective verified count by 2, likely flooring it to −999 until it proves itself again.

This is what makes the system actually learn rather than just count.

6.14 Segments

Scores are per (vendor, task, segment). A vendor can be excellent for us_saas and poor for eu_enterprise. Today the caller passes the segment (default global); later it can be derived from country/TLD/company size. Until a segment has data, its vendors share the prior score and tie-break by id.

6.15 Lazy recalculation

There is no always-on scheduler. Instead, after each logged attempt we check how many logs have appeared since provider_scores.updated_at; at 20 or more we recompute inline. You can also force it with recalc. This is cheap (a few aggregates over a 30-day window) and removes a class of "why didn't the score update" bugs.

7. A request, step by step

This is the exact control flow in router.enrich.

INPUT: EnrichmentRequest(task_type, segment, names, domain, linkedin, email,
                          max_cost_budget, request_id)

1. Reject nothing silently — Pydantic validates the request.
2. budget = request.max_cost_budget  OR  DEFAULT_MAX_BUDGET ($0.10)
3. lookup_hash = SHA256(task_type | normalized_identity)
4. IF cache row exists AND not expired:
       return cached positive (data, source_provider) or cached negative
5. Ensure score rows exist (recalc once if a provider is missing a score)
6. rows = active providers for (task, segment), cooldown elapsed,
          ORDER BY routing_score DESC
7. IF len(rows) > 1 AND random() < 0.05:
       promote a random lower-ranked provider to slot 1 (explore)
8. FOR each provider in order:
       a. IF spent + cost_attempt + cost_match > budget:
              trace "skipped_budget"; continue
       b. adapter = registry[provider]; if none: trace "error"; continue
       c. result = adapter.fetch(req)        # timed, exceptions caught
       d. IF error_code is no_api_key/missing_inputs:
              trace "skipped_unconfigured"; continue   # no bill, no failure
       e. attempted += 1; spent += cost
       f. IF transport error (429/5xx/timeout):
              increment breaker; maybe cooldown; log; trace "error"; continue
       g. reset breaker; IF not matched: log; trace "miss"; continue
       h. verified = verifier.verify(task, value, payload)
       i. log matched + verified + result_value
       j. IF verified:
              write positive cache; maybe recalc; RETURN success
          ELSE continue (matched but unverified is not a win)
9. IF attempted > 0 AND no transport error AND no budget skip AND no match:
       write negative cache (7 days)
10. maybe recalc; RETURN failure with full trace
Why keep going after an unverified match? A vendor may return an address that passes syntax but has no MX. That is not a usable result. Trying the next vendor may produce a verifiable one. Note that a waterfall that did get a match but could not verify it does not write a negative cache — we did not prove the person is unfindable.

8. Verification logic

Verification is task-dispatched: the same "verified" word means different checks for different data.

TaskCheck todayWhy
work_emailRegex syntax + DNS MX lookup (A-record fallback)Cheap, local, and reliable. Raw SMTP probing on port 25 fails from most cloud/VPS IPs and gets blocked.
mobile_phoneE.164 normalization, 7–15 digitsCatches truncation and formatting garbage without a paid carrier lookup.
company_firmographicsRequired keys non-empty: name, domain, and employee_count or industryEnsures a returned company record is actually usable.

A paid HTTP verifier (MillionVerifier, ZeroBounce, etc.) can be added behind a config flag later without touching the router — the verifier is already a swappable function.

9. Providers and adapters

Each vendor is an isolated module implementing one interface. The base class guarantees the router never sees an exception.

class BaseProvider:
    id: str
    task_types: tuple[str, ...]

    async def _fetch(self, req) -> ProviderResult: ...   # vendor-specific

    async def fetch(self, req) -> ProviderResult:         # what router calls
        start = perf_counter()
        try:
            result = await self._fetch(req)               # normalizes vendor JSON
        except Exception as exc:
            result = ProviderResult.error(f"exception:{type(exc).__name__}")
        result.latency_ms = measured
        return result
AdapterTaskStatus
hunter.pywork_emailLive and verified (key present, Starter plan).
prospeo.pywork_emailWired; skips cleanly until a key exists.
findymail.pywork_emailWired; skips cleanly until a key exists.
apollo.pywork_emailKey present but Apollo's API is usually paid-gated; skips/errors cleanly.
mock.pyallDeterministic, no network, used by --dry-run and tests.

Adapters normalize raw vendor JSON into a single ProviderResult with matched, value, data, status_code, error_code, and latency_ms. That normalization is what lets the router treat every vendor identically.

Phone and firmographics live adapterstodoVerification logic exists; no vendor adapters for those tasks yet.
Known mathematical caveats.
  • Small samples dominate: a single slow success can rank below untested vendors (observed with Hunter). Priors are conservative on purpose; a minimum-sample gate is a possible tuning knob.
  • MX only proves the domain accepts mail; it does not prove the mailbox exists. Only feedback closes that gap.
  • Latency is measured client-side, so it includes our own network, not just vendor service time.
  • Costs are configured estimates, not invoice truth.
  • Weights and priors are judgment calls; they should be tuned against real business outcomes.

13. What it can become after later phases

Phase 3 — HTTP service

  • POST /v1/enrich, GET /v1/scorecard, POST /v1/feedback on 127.0.0.1:8790 (the port is already declared, optional).
  • A webhook endpoint your outreach tool calls on bounce/reply, replacing the manual feedback command.
  • A tiny dashboard over the scorecard: which vendor is winning, by segment, at what cost.

Phase 4 — deeper intelligence

  • Batch/portfolio routing: decide over a whole list, not one record — a knapsack that spends a fixed budget maximizing expected verified hits.
  • Better bandits: Thompson sampling or UCB instead of fixed epsilon, for faster learning with less waste.
  • Consensus and confidence: when two vendors agree, raise confidence; when they disagree, route to a verifier.
  • Auto-segmentation: derive segment from country/TLD/headcount instead of trusting the caller.
  • Adaptive TTLs: learn how long each vendor's data stays good and set TTL per vendor/segment.
  • Spend forecasting and alerts: project monthly cost, warn on anomalies, reconcile invoices.
  • Vendor SLA monitoring: the same logs double as an uptime/quality monitor per vendor.
  • Multi-task routing: phone and firmographics with their own vendors and verifiers.
  • Human-in-the-loop review: queue low-confidence values for manual checks.

What it could optimize end to end

Not just "get an email" but "get the cheapest set of verified contacts that maximizes reply rate", using feedback from real replies — turning a data tool into a revenue-yield optimizer.

Clay is a popular GTM data platform. Among many features it offers waterfall enrichment: for each row it tries one provider, then the next, until a field is filled, plus AI research and a large library of integrations. 16. How to run it, command by command

All commands are invoked through the shared runner from the workspace root.

# 1. Create the database and seed providers (free)
.venv\Scripts\python.exe scripts\engines.py run enrichment-arbiter init

# 2. Check dependencies, secrets, and db
.venv\Scripts\python.exe scripts\engines.py run enrichment-arbiter doctor

# 3. See counts and the current scoreboard
.venv\Scripts\python.exe scripts\engines.py run enrichment-arbiter status

# 4. Add or update a vendor (example)
.venv\Scripts\python.exe scripts\engines.py run enrichment-arbiter provider add `
  --id hunter --task work_email --cost-match 0.02 --max-rps 5

# 5. Real enrich, with a hard dollar cap
.venv\Scripts\python.exe scripts\engines.py run enrichment-arbiter enrich `
  --task work_email --first-name Ada --last-name Lovelace `
  --domain acme.com --max-budget 0.10

# 6. No-spend rehearsal
.venv\Scripts\python.exe scripts\engines.py run enrichment-arbiter enrich `
  --dry-run --task work_email --first-name Ada --last-name Lovelace `
  --domain acme.com --max-budget 0.10

# 7. Rankings, rates, ECPVH
.venv\Scripts\python.exe scripts\engines.py run enrichment-arbiter scorecard --task work_email

# 8. Force a score recompute
.venv\Scripts\python.exe scripts\engines.py run enrichment-arbiter recalc

# 9. Feed back a bounce (webhook equivalent)
.venv\Scripts\python.exe scripts\engines.py run enrichment-arbiter feedback `
  --email someone@acme.com --event bounce

# 10. Active benchmark (spends; requires both flags)
.venv\Scripts\python.exe scripts\engines.py run enrichment-arbiter golden-probe `
  --yes --max-budget 0.50

Every command prints one JSON object to stdout; errors go to stderr with a non-zero exit. Run artifacts are written under runs/.
